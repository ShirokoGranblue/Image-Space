## 1. 目标与产品语气

AstralSpace 是一个围绕图片整理、分享和公开发现展开的空间。介绍性文案负责内容、氛围与主题，字段、权限、错误和危险操作负责让用户立即知道下一步。

最终语气遵循以下规则：

- 英文品牌名始终写作 `AstralSpace`，不设置固定中文副标题。
- 不再使用“星图、轨道、坐标、宇宙”等贯穿式隐喻。
- 标题使用完整句，但不刻意追求奇异表达。
- 用户名、邮箱、验证码、密码、文件格式、文件大小、IP 地址、请求路径、风险等级、删除、注销、权限拒绝和加载失败保持直接。
- 登录、注册、上传、搜索、筛选、下载、选择、复制、点赞等动作词保持明确。
- 介绍页侧重图片本身、创作内容、观看氛围和分享关系，不把功能清单当作主标题。
- 用户生成的图片名称、描述、评论、标签和个人介绍不重写。

参考方向：

- [Unsplash](https://unsplash.com/)：借鉴“先呈现内容与创作者，再呈现工具”的信息优先级。
- [Are.na](https://www.are.na/about)：借鉴保存内容、持续整理与建立集合的克制语气。
- [Cosmos](https://www.cosmos.so/)：借鉴图片详情中图片区与信息区属于同一整体的结构。
- [Anthropic](https://www.anthropic.com/)：借鉴无图标、粗体无衬线文字品牌的页头处理；不照搬全大写品牌形式。

## 2. 实施边界

### 2.1 本次前端实施允许包含

- 用户可见文字、placeholder、Toast、弹窗、空状态、加载状态和错误状态。
- 与可见名称机械同步的 `aria-label`、`title`、`alt` 和测试断言；这些不可视文本不单独进行风格化创作。

- 已明确批准的交互调整：下载按钮改为格式菜单。
- 已明确批准的临时前端统计调整：Profile 当前页只汇总 `PUBLIC` 图片的点赞数。
- 通知相对时间的前端显示逻辑。

### 2.2 本次明确不包含

- 新增或修改路由；`AstralSpace` 品牌链接继续指向现有 `/home`。
- 未登录状态下的动态品牌路由分支。
- 后端、数据库、API 协议、权限判定、部署和生产同步。
- 新字体服务、新图片资产、新图标系统或新颜色变量。
- 未在本稿中点名的页面重排、组件重构、动画和功能。
- 为了顺手统一而修改其他技术字段或用户内容。

## 9. 图片详情 `/image/:uuid`

- 参考 Cosmos 详情页，将图片区和信息区合并为一个整体容器。
- 桌面端为左侧图片区、右侧信息区，中间使用细分隔线；不再保留两个独立外框和中间大间距。

### 10.2 相对时间

固定规则：

```text
不足 1 分钟：刚刚
1–59 分钟：N分钟前
1–23 小时：N小时前
24 小时及以上：N天前
```

- 不显示完整日期，即使超过 24 小时仍显示 `47天前`、`365天前`。
- 时间放在正文最前，与正文处于同一个文本流。
- 不使用单独时间行。
- 文本允许在长用户名或长图片名称时自然换行，不强制 `nowrap`。

最终句式：

```text
47天前 ShirokoGranblue 点赞了《图片名称》
3小时前 ShirokoGranblue 评论了《图片名称》
10分钟前 ShirokoGranblue 点赞了你的评论
```

只有通知正文中的图片名称使用书名号。上传失败、文件格式、下载、删除确认和分享 Toast 中的文件名不使用书名号。

风险：本次相对时间基于客户端当前时间，设备时钟错误会影响结果；后端时间契约列入延期清单。

## 15. 后期需要改后端的事项（本轮不实施）

### 15.1 用户公开获赞总数

目标：Profile 的 `获赞`始终表示该用户全部 `PUBLIC` 图片收到的累计点赞数，而不是当前分页数据。

建议契约：

- 在用户公开资料响应或专用统计响应中返回明确字段，例如 `publicLikeCount`；具体字段名应在后端任务中结合现有 VO 命名确认，不在本稿直接定死。
- 统计范围只包含 `visibility = PUBLIC` 的图片。
- `SPECIFIED`和`PRIVATE`均不参与公开获赞。
- 图片被软删除或正式删除后，不再参与统计。
- 点赞与取消点赞后，总数应同步变化。
- 图片从 `PUBLIC`变成 `SPECIFIED`或`PRIVATE`时，应从公开获赞中扣除该图片的现有点赞数。
- 图片从非公开变回 `PUBLIC`时，应重新纳入该图片的现有点赞数。
- 图片所有者变化若未来被支持，也必须同步统计归属；当前没有此需求，不新增功能。

实现建议与风险：

- 优先采用数据库实时聚合或经过一致性验证的缓存，不在用户表中随意增加容易漂移的计数器。
- 如果使用冗余计数器，点赞、取消点赞、删除和可见性修改必须处于一致事务或具备可恢复的事件机制。
- 高并发点赞/取消点赞必须防止重复累加、重复扣减和负数。
- 需要考虑历史数据回填与校验，不能只从上线后的新事件开始累计。

最低测试要求：

1. 多页公开图片的点赞能够返回正确总和。
2. `SPECIFIED`和`PRIVATE`图片的点赞不计入。
3. PUBLIC → PRIVATE / SPECIFIED 时正确扣减。
4. PRIVATE / SPECIFIED → PUBLIC 时正确恢复。
5. 点赞、取消点赞和重复请求不会产生错误总数。
6. 删除图片后总数正确。
7. 所有者查看与访客查看返回相同的公开获赞口径。

### 15.2 通知时间字段与时区契约

目标：后端提供稳定、无歧义的事件时间，前端负责显示`刚刚 / N分钟前 / N小时前 / N天前`。

后端要求：

- `createTime`使用统一、可解析并携带时区含义的格式，优先 ISO 8601 或项目统一的 UTC 时间契约。
- 所有通知类型使用同一时间字段和同一序列化规则。
- 不由后端返回`47天前`等展示字符串，避免缓存、语言和客户端时间变化导致文本过期。
- 明确未来时间、空时间和错误时间的处理；前端不应因为单条时间异常而使整个通知抽屉失败。
- 若系统依赖数据库本地时区，应在后端任务中验证 JVM、数据库和序列化时区一致性。

最低测试要求：

1. 不同时区下序列化结果表示同一时刻。
2. 夏令时切换不改变事件真实顺序。
3. 所有通知类型均返回可解析的 `createTime`。
4. 分页、轮询和 SSE 返回的时间格式一致。
5. 缺失或异常时间有稳定的降级契约。
